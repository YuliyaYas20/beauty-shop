# ADR 0002: Шарова архітектура модульного моноліту

- **Статус:** Прийнято
- **Дата:** 2026-11-17

## Контекст

Для підтримки чистоти коду в межах модульного моноліту та забезпечення можливості паралельної роботи учасників команди необхідно зафіксувати чітку структуру каталогів і правила взаємодії між компонентами.

## Рішення

Запроваджено тришарову структуру коду в межах проєкту:

1. **`api/`** — шар представлення (контролери та Express-роути). Приймає HTTP-запити, витягує параметри/тіло запиту (DTO), викликає відповідний метод сервісу та формує HTTP-відповідь зі статусом згідно з OpenAPI-контрактом.
2. **`service/`** — шар бізнес-логіки (use-cases). Виконує валідацію вхідних даних (перевірка обов'язкових полів, невід'ємність ціни та кількості), реалізує бізнес-операції, виконує мапінг між DTO та доменними сутностями й взаємодіє зі сховищем даних (SQLite).
3. **`domain/`** — шар доменної моделі. Містить сутність `Product`, її атрибути та базові інваріанти.

## Напрямок залежностей та заборонені зв'язки

- Залежності спрямовані строго зверху вниз: **`api/` → `service/` → `domain/`**.
- **Заборонено:** шар `api/` не має права звертатися напряму до бази даних SQLite або містити бізнес-логіку та правила валідації.
- **Заборонено:** шар `domain/` не залежить від фреймворку Express, HTTP-запитів чи деталей реалізації БД.

## Наслідки

- Спрощується написання юніт-тестів для шару `service/` без необхідності піднімати HTTP-сервер.
- Чітке розмежування відповідальності дозволяє розробляти та тестувати API-контракт і бізнес-логіку незалежно.
